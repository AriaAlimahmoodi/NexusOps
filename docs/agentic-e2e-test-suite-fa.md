# راهنمای آزمون پذیرش End-to-End عامل NexusOps

## هدف

فایل `workflows/nexusops-agentic-e2e-test-suite.json` مسیر واقعی Chat Trigger را فراخوانی می‌کند؛ بنابراین برخلاف MCP Runtime Test Suite، اجرای Ollama Planner، اعتبارسنجی Plan، MCP، Elasticsearch، Answer Writer و پاسخ نهایی را در یک آزمون زنجیره‌ای درگیر می‌کند.

این مجموعه پنج سناریو دارد و درخواست‌ها را با Loop Over Items نسخه ۳ و اندازه batch برابر ۱، به‌صورت ترتیبی اجرا می‌کند تا مدل محلی درگیر چند درخواست هم‌زمان ناخواسته نشود. خروجی شماره ۱ حلقه، درخواست را به Chat Trigger می‌فرستد و خروجی شماره ۰ (Done) پس از پایان همه دورها به ارزیاب متصل است.

## پیش‌نیازهای اجرا

1. Elasticsearch و MCP Server را اجرا کنید.
2. Ollama را اجرا کنید و مطمئن شوید مدل `qwen3:4b` در دسترس است.
3. n8n محلی را اجرا کنید.
4. Workflow اصلی `NexusOps-Agentic-Workflow` را در n8n باز کنید و آن را **Activate/Publish** کنید. Chat Trigger عمومی باید فعال باشد؛ اجرای این مجموعه در حالت غیرفعال بودن workflow اصلی با خطای webhook مواجه می‌شود.
5. شناسه webhook در Chat Trigger باید با شناسه ثبت‌شده در فایل workflow مخزن یکسان باشد. اگر هنگام Import یا بازسازی workflow شناسه عوض شد، URL نود `Invoke Production Chat Trigger` باید با Chat URL نمایش‌داده‌شده در n8n هماهنگ شود.

## Import و اجرا

1. فایل `workflows/nexusops-agentic-e2e-test-suite.json` را در n8n از مسیر Import from File وارد کنید.
2. workflow آزمون را باز کنید؛ نیازی به فعال‌کردن آن نیست.
3. Manual Trigger را با Execute Workflow اجرا کنید.
4. منتظر بمانید پنج درخواست ترتیبی کامل شوند. برای هر درخواست، زنجیره کامل مدل و سرویس‌ها اجرا می‌شود و زمان پاسخ ممکن است به سخت‌افزار و بار Ollama وابسته باشد.
5. خروجی نود `Evaluate Agent E2E Results` را بررسی کنید. معیار نهایی `summary.overall` و جزئیات هر مورد در `results` است.

## سناریوهای پذیرش

| شناسه | مسیر | معیار |
|---|---|---|
| A01 | پرسش شمارش فارغ‌التحصیلان | عدد ۳۰ در پاسخ واقعی Agent وجود داشته باشد |
| A05 | تجمیع Scalar فارغ‌التحصیلان | شمارش ۳۰ و میانگین مدت اشتغال ۶٫۹۳ هر دو در پاسخ باشند |
| A02 | بازیابی درس C002 | شناسه C002 و نام «ساختمان داده» در پاسخ دیده شوند |
| A03 | درخواست دوهدفه | پاسخ شامل شمارش ۳۰ و نتیجه شکاف مهارتی باشد و هشدار صریح incomplete/partial_failure نداشته باشد |
| A04 | درخواست خارج از دامنه | Domain Gate درخواست قیمت بیت‌کوین را رد کند |

اعداد و نام مورد انتظار از داده‌های قراردادی فعلی پروژه گرفته شده‌اند. اگر داده‌های Elasticsearch عمداً تغییر کردند، معیارهای ثابت این مجموعه نیز باید با داده مرجع جدید بازبینی شوند.

## تفسیر

- `PASS`: assertion محتوایی همان سناریو روی پاسخ HTTP واقعی برقرار شده است.
- `FAIL`: پاسخ، status HTTP یا محتوای مورد انتظار با قرارداد آزمون سازگار نیست؛ جزئیات در `detail` آمده است.
- `summary.overall = PASS`: هر پنج درخواست پاسخ قابل ارزیابی داده‌اند و تمام assertionهای تعریف‌شده موفق بوده‌اند.

این آزمون، یک پذیرش End-to-End مبتنی بر پاسخ واقعی است؛ اما به‌تنهایی تعداد Planهای تولیدشده را از داخل اجرای n8n استخراج نمی‌کند و اثبات قطعی اجرای دو Plan مستقل نیست. سناریوی A03 یک درخواست چندهدفه واقعی به Planner می‌دهد و خروجی چندبخشی مورد انتظار را بررسی می‌کند. همچنین این مجموعه هنوز fault injection برای شکست عمدی یک فراخوانی MCP و آزمون هم‌زمانی چند execution مستقل انجام نمی‌دهد؛ این دو موضوع نباید از PASS این مجموعه استنباط شوند.

## عیب‌یابی

- HTTP 404 یا webhook not registered: workflow اصلی را Activate/Publish کنید و Chat URL را با webhookId فعلی تطبیق دهید.
- HTTP 401/403: تنظیمات Authentication در Chat Trigger را بررسی کنید؛ workflow فعلی باید با روش دسترسی مورد انتظار محلی سازگار باشد.
- خطای اتصال Ollama: سرویس Ollama و مدل `qwen3:4b` را بررسی کنید.
- شکست A01 یا A02: جزئیات پاسخ و داده مرجع Elasticsearch را بررسی کنید؛ خروجی مدل به‌تنهایی منبع حقیقت نیست.
- شکست A03: execution اصلی را در n8n باز کنید و خروجی Query Planner، Validate Plan، MCP Parse Result و Compose Final را بررسی کنید.
- شکست A04: منطق Domain Gate و واژه‌های ورودی را بررسی کنید.

## مرز اعتبار آزمون\n\nارزیاب E2E پاسخ نهایی HTTP را با assertionهای محتوایی بررسی می‌کند. این ارزیابی اثبات مستقیم تعداد Planهای داخلی، تطبیق عددی تمام Aggregationها با Query مستقل Kibana یا آزمون fault injection نیست. برای این موارد به‌ترتیب باید اجرای داخلی n8n بررسی شود، Runbook تحلیلی اجرا شود و تست‌های قابلیت اطمینان Python مورد استفاده قرار گیرند.\n\n## تفاوت با MCP Runtime Test Suite

- MCP Runtime Test Suite قرارداد پروتکل، ابزارها و عملیات analytics را بدون Ollama آزمایش می‌کند.
- Agentic E2E Acceptance Suite مسیر واقعی مکالمه تا پاسخ را با Ollama آزمایش می‌کند.
- برای پذیرش کامل محصول، هر دو مجموعه لازم‌اند؛ هیچ‌کدام جایگزین دیگری نیست.
