# پذیرش یکپارچه‌ی سرتاسری NexusOps

## اصل آزمون

در پذیرش زنده‌ی پروژه فقط یک مسیر اجرا می‌شود: **Workflow اصلی NexusOps از Chat Trigger تا پاسخ نهایی**. مجموعه‌ی زیر مستقیماً MCP را فراخوانی نمی‌کند؛ تمام ۱۸ درخواست را به Chat Trigger اصلی می‌فرستد تا Ollama Planner، اعتبارسنجی Plan، MCP، Elasticsearch، نرمال‌سازی نتایج، Answer Writer و Compose Final در یک زنجیره‌ی واقعی آزموده شوند.

درخواست‌ها با Loop Over Items و batch size برابر ۱، ترتیبی اجرا می‌شوند. برای هر سناریو session مستقل ساخته می‌شود تا نتیجه‌ی یک درخواست به درخواست دیگر نسبت داده نشود.

## پیش‌نیازها

1. Elasticsearch و Kibana را اجرا کنید.
2. MCP Server را در محیط مجازی پروژه اجرا کنید.
3. Ollama و مدل `qwen3:4b` را اجرا کنید.
4. n8n محلی را اجرا کنید.
5. Workflow اصلی `NexusOps-Agentic-Workflow` را Activate/Publish کنید.
6. Chat URL نود اصلی را با URL نود `Invoke Production Chat Trigger` در فایل آزمون تطبیق دهید؛ اگر n8n هنگام Import شناسه‌ی webhook را تغییر داده است، URL آزمون باید به‌روز شود.

## اجرای تنها آزمون زنده

1. فایل `workflows/nexusops-agentic-e2e-test-suite.json` را در n8n Import کنید.
2. Workflow آزمون را باز کنید؛ آن را Activate نکنید.
3. Manual Trigger را اجرا کنید.
4. تا پایان ۱۳ درخواست ترتیبی صبر کنید.
5. خروجی `Evaluate Agent E2E Results` را بررسی کنید. معیار پذیرش `summary.overall = PASS) و موفقیت تمام موارد `results) است.

## مرزهای اعتبار

- این مجموعه پاسخ HTTP واقعی Workflow اصلی را بررسی می‌کند؛ بنابراین پذیرش زنده‌ی جداگانه‌ای برای MCP Runtime اجرا نمی‌شود.
- تست‌های Python در CI همچنان قراردادهای داخلی، اعتبارسنجی، parser، correlation، ساختار Workflow و رگرسیون‌ها را بررسی می‌کنند؛ این‌ها اجرای زنده‌ی یک Workflow موازی نیستند.
- فایل `workflows/nexusops-mcp-runtime-test-suite.json` فقط به‌عنوان ابزار تشخیصی اختیاری برای زمانی نگه داشته شده که خطا نیازمند جداسازی لایه‌ی MCP باشد؛ در پذیرش معمول اجرا نمی‌شود.
- A03 یک درخواست چندهدفه را از بیرون بررسی می‌کند؛ به‌تنهایی اثبات نمی‌کند Planner دقیقاً چند Plan ساخته است. برای این ادعا باید metadata اجرای داخلی بررسی شود.
- این مجموعه fault injection و هم‌زمانی را پوشش نمی‌دهد. اسکریپت concurrency فقط smoke test چند session مستقل روی همان Chat Trigger اصلی است و اثبات ترتیب‌دهی درخواست‌های یک session نیست.
- برای صحت عددی تحلیل‌های مهم، خروجی‌های زنده باید با Query مستقل در Kibana Dev Tools تطبیق داده شوند.

## عیب‌یابی

- خطای webhook یا HTTP 404: فعال بودن Workflow اصلی و URL دقیق Chat Trigger را بررسی کنید.
- خطای Ollama: اجرای سرویس و در دسترس بودن مدل `qwen3:4b` را بررسی کنید.
- خطای MCP: لاگ MCP Server و execution اصلی n8n را از مرحله‌ی Initialize تا Parse Result بررسی کنید.
- شکست A03: خروجی‌های Query Planner، Validate Plan، MCP Parse Result، Prepare LLM Context و Compose Final را در همان execution بررسی کنید.
- شکست عددی: ابتدا داده‌ی واقعی را در Kibana بررسی کنید؛ assertion ثابت نباید با حدس تغییر داده شود.
