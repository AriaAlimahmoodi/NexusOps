# گزارش وضعیت ریفکتوری NexusOps

**تاریخ:** ۹ نوامبر ۲۰۲۶  
**شاخه:** `refactor/integration-foundation`  
**شاخهٔ `main`:** در این ریفکتوری تغییر داده نشده است.

## ۱. هدف ریفکتوری

هدف، تبدیل اتصال اولیهٔ ELK، MCP، n8n و مدل زبانی محلی به یک معماری منسجم، قابل توسعه و قابل اتکا بوده است؛ با حفظ راهکارهای رایگان و اجرای مدل از طریق Ollama، بدون وابستگی اجباری به API پولی.

معماری هدف:

```text
User → Local LLM (Ollama) → MCP → Analytics/Search Tools → Elasticsearch
                         ↘ n8n orchestration
```

## ۲. کارهای انجام‌شده

### موتور تحلیل عمومی
- موتور تحلیلی موجود به‌عنوان مسیر واحد تحلیل حفظ و از طریق MCP در دسترس قرار گرفته است؛ موتور موازی و تکراری ساخته نشده است.
- عملیات `select`، `count` و `aggregate` پیاده‌سازی/یکپارچه شده‌اند.
- معیارها شامل شمارش اسناد، شمارش مقادیر، sum، avg، min، max و cardinality هستند.
- مسیر اعتبارسنجی، حل فیلد، ساخت Query/Aggregation، اجرا از طریق Adapter و قالب‌بندی خروجی تفکیک شده است.

### رجیستری داده
پروفایل پنج Dataset در رجیستری متمرکز شده‌اند:
- `university_graduates`
- `university_courses`
- `course_graduate_records`
- `labor_market`
- `skill_mapping`

رجیستری مرجع فیلدها، نوع داده، نقش مجاز فیلد و قابلیت‌های Aggregation است.

### فیلترهای تحلیلی
- فیلترهای تو‌در‌تو با منطق AND و OR پشتیبانی می‌شوند.
- عملگرهای eq، neq، in، not_in، gt، gte، lt، lte، between، exists و not_exists در قرارداد فیلتر وجود دارند.
- سازگاری با آرگومان‌های تخت قدیمی در مرز MCP حفظ شده است.

### برنامه‌ریز زبان طبیعی
- کاتالوگ Datasetها و فیلدهای مجاز در اختیار برنامه‌ریز محلی قرار می‌گیرد.
- درخواست طبیعی به Plan ساخت‌یافته برای `analytics_query` تبدیل می‌شود.
- خروجی مدل پیش از ارسال به MCP اعتبارسنجی می‌شود.
- مسیرهای قطعی برای برخی الگوهای بدون ابهام به‌عنوان fallback وجود دارند.
- ارقام فارسی/عربی در برخی الگوهای قطعی نرمال می‌شوند.
- اعتبارسنجی سمت سرور همچنان مرجع نهایی پذیرش درخواست است.

### MCP و ابزارهای تخصصی
پنج ابزار زیر در فهرست ابزارهای MCP موجود و در preflight اخیر تأیید شده‌اند:
- `analytics_query`
- `search_elasticsearch`
- `get_top_market_skills`
- `get_top_skill_gaps`
- `get_market_skill_details`

توضیحات ابزارها تفکیک جست‌وجوی سندی از تحلیل تقاضای بازار و شکاف مهارتی را روشن‌تر کرده‌اند. انتقال MCP از نوع Streamable HTTP است.

### قابلیت اطمینان زمان اجرا
- تاریخچه، حافظه و شواهد تأییدشده برای هر conversation_id جدا شده‌اند.
- Turnهای یک مکالمه با قفل‌گذاری مرتب می‌شوند.
- حافظهٔ درون‌فرایندی با ظرفیت محدود و سیاست LRU کنترل می‌شود.
- برای تلاش‌های MCP، Session مستقل ایجاد می‌شود.
- Retry محدود به خطاهای انتقال و Timeout است؛ خطاهای منطقی و اعتبارسنجی Retry نمی‌شوند.
- عملیات Blocking در Thread جدا از Event Loop اجرا و با Semaphore محدود می‌شوند.
- ظرفیت Worker تا پایان Thread حتی هنگام لغو درخواست حفظ می‌شود.
- Elasticsearch Client در مسیرهای موفق و خطا بسته می‌شود.
- پاسخ خطای استاندارد و Logging ساخت‌یافته با شناسهٔ هم‌بستگی اضافه شده‌اند.

### تست و مستندات
- تست‌های برنامه‌ریزی، Pipeline تحلیلی، مرز ابزار، رجیستری Dataset و قابلیت اطمینان زمان اجرا اضافه شده‌اند.
- اسکریپت preflight و Runbook پذیرش تحلیلی تهیه شده‌اند.
- مستند معماری Runtime Reliability اضافه شده است.

## ۳. وضعیت تأییدشده

### تست‌های خودکار
آخرین نتیجه‌ای که پیش‌تر از اجرای محلی گزارش شده بود:

```text
99 passed
```

این نتیجه مربوط به پیش از اضافه‌شدن سه تست جدید preflight است. نتیجهٔ نهایی باید پس از Pull تغییرات این مرحله دوباره ثبت شود.

### پیش‌بررسی زنده
کاربر در ۹ نوامبر ۲۰۲۶ اجرای preflight را با `ok: true` گزارش کرده است:

| مؤلفه | نتیجه |
|---|---|
| Elasticsearch | اتصال موفق؛ نسخهٔ 9.5.5؛ کلاستر `my-elk-cluster` |
| Ollama | مدل `qwen3:4b` موجود |
| MCP | اتصال موفق؛ هر پنج ابزار الزامی حاضر |
| n8n | پاسخ HTTP با وضعیت 200 |

این پیش‌بررسی دسترسی سرویس‌ها را تأیید می‌کند، نه اجرای موفق Workflow یا صحت عددی تحلیل‌ها را.

## ۴. تغییرات همین مرحله

preflight اکنون علاوه بر اتصال به Elasticsearch، رجیستری Datasetها را می‌خواند و وجود Index فیزیکی متناظر با هر Dataset ثبت‌شده را بررسی می‌کند. خروجی شامل وضعیت هر Dataset/Index و فهرست Indexهای مفقود است. اگر کلاستر در دسترس باشد اما Index موردنیاز وجود نداشته باشد، بررسی Elasticsearch ناموفق خواهد بود.

سه تست جدید برای این حالت‌ها اضافه شده‌اند:
1. وجود همهٔ Indexهای ثبت‌شده.
2. مفقود بودن یک Index.
3. بروز خطا هنگام بررسی Index و اطمینان از بسته‌شدن Client.

دامنهٔ بررسی n8n نیز در خروجی مشخص شده است: پاسخ HTTP فقط دسترسی به URL پایه را ثابت می‌کند، نه فعال بودن Workflow، صحت Credentialها یا اجرای موفق Nodeها.

## ۵. کارهای باقی‌مانده

### اولویت اول: پذیرش سرتاسری در n8n و تطبیق عددی
این مهم‌ترین مرحلهٔ باقی‌مانده است. سناریوها باید از طریق Workflow واقعی اجرا شوند:

| سناریو | معیار پذیرش |
|---|---|
| شمارش فارغ‌التحصیلان سال ۱۴۰۲ | تطابق با `university_graduates/_count` |
| میانگین ارتباط شغلی و مدت اشتغال به تفکیک رشته | تطابق تمام Bucketها و دو معیار با Aggregation مستقل |
| فیلتر هم‌زمان `market_demand >= 4.8` و `market_gap >= 2.5` | حضور هر دو شرط در یک AND و تطابق رکوردها |
| جست‌وجوی G0001 و C002 | بازیابی شناسهٔ دقیق از ابزار جست‌وجوی سندی |
| رتبه‌بندی تقاضا و شکاف مهارتی | انتخاب ابزار تخصصی و تطابق مقادیر و ترتیب |
| مقایسهٔ چندمعیارهٔ مهارت‌ها | محاسبهٔ تقاضا و شکاف و مرتب‌سازی بر اساس معیار درخواستی |
| درخواست‌های هم‌زمان | عدم اختلاط Dataset، فیلتر، خروجی و شواهد مکالمات |
| چند Turn در یک مکالمه | حفظ ترتیب و ارجاع درست به شواهد همان مکالمه |

نتایج عددی باید با Kibana Dev Tools به‌صورت مستقل بررسی شوند.

### اولویت دوم: تکمیل برنامه‌ریز زبان طبیعی
- پوشش عبارت‌های فارسی/انگلیسی و صورت‌های محاوره‌ای بیشتر شود.
- درخواست مبهم از درخواست قابل برنامه‌ریزی تفکیک شود.
- Planهای معادل برای عبارت‌های هم‌معنا تولید شوند.
- محدودیت تک‌Dataset بودن هر Query و نبود Join فرضی صریحاً کنترل شود.
- رفتار Qwen3:4b برای درخواست‌های طولانی و چندشرطی در Workflow واقعی ارزیابی شود.

### اولویت سوم: قرارداد پاسخ و خطا
- یکسان‌سازی جزئیات خطا در همهٔ ابزارهای MCP.
- تعیین سیاست صفحه‌بندی و حجم خروجی برای نتایج بزرگ.
- تعیین رفتار مقادیر تهی و Bucketهای خالی.
- بررسی Timeout انتها‌به‌انتها و ثبت زمان پاسخ، نرخ خطا و Retry.

### اولویت چهارم: امنیت و استقرار
- فعال‌سازی TLS verification با CA معتبر؛ تنظیم فعلی `verify_certs=false` فقط برای محیط محلی مناسب است.
- تعریف احراز هویت و کنترل دسترسی برای MCP و n8n در محیط غیرمحلی.
- سخت‌سازی مدیریت Secretها، محدودیت نرخ و مصرف منابع.
- آماده‌سازی Docker پس از تکمیل پیاده‌سازی و پذیرش، مطابق تصمیم پروژه.

### اولویت پنجم: پایداری چندکاربره
حافظهٔ مکالمه فعلی درون‌فرایندی است؛ با Restart از بین می‌رود و میان چند Worker مشترک نیست. برای استقرار چندپردازه‌ای باید ذخیره‌سازی مشترک و پایدار Session و شواهد طراحی شود.

## ۶. ترتیب اجرایی پیشنهادی ادامه

1. Pull آخرین تغییرات و اجرای تست‌های خودکار.
2. بررسی خروجی جدید preflight و تأیید پنج Index ثبت‌شده.
3. اجرای سناریوهای پذیرش از n8n واقعی.
4. تطبیق مستقل اعداد با Elasticsearch در Kibana Dev Tools.
5. رفع ایرادهای کشف‌شده در یک بستهٔ اصلاحی منسجم.
6. تکمیل پوشش زبان طبیعی و قرارداد پاسخ.
7. سخت‌سازی امنیت و سپس آماده‌سازی Docker.

## ۷. جمع‌بندی

بخش عمدهٔ زیرساخت نرم‌افزاری ریفکتوری شده است: موتور تحلیل، رجیستری داده، برنامه‌ریز محلی، مرز MCP، مدیریت مکالمه، کنترل هم‌زمانی، مدیریت خطا، Logging و preflight.

**گلوگاه اصلی فعلی، اثبات عملکرد سرتاسری با داده‌های Elasticsearch و اجرای واقعی Workflow در n8n است.** تا پیش از تأیید سناریوهای عددی، فیلترهای ترکیبی و هم‌زمانی، نباید پذیرش عملیاتی پروژه را نهایی‌شده دانست.
