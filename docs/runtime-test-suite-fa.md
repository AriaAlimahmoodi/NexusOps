# راهنمای اجرای آزمون‌های Runtime در n8n

## هدف

فایل `workflows/nexusops-mcp-runtime-test-suite.json` یک workflow مستقل و قابل Import برای آزمون مسیر واقعی n8n → MCP → Elasticsearch است. این مجموعه به Ollama و مدل زبانی وابسته نیست؛ بنابراین نتایج آن برای بررسی قرارداد MCP و موتور تحلیل، قطعی‌تر و تکرارپذیرتر از آزمون مبتنی بر prompt هستند.

## پیش‌نیازها

پیش از اجرای آزمون:

1. Elasticsearch و Kibana را طبق پیکربندی محلی پروژه اجرا کنید.
2. MCP Server را از ریشه مخزن و در محیط مجازی پروژه اجرا کنید.
3. n8n محلی را اجرا کنید.
4. در دسترس بودن این endpointها را بررسی کنید:
   - Elasticsearch: `https://127.0.0.1:9200` (یا URL ثبت‌شده در فایل `.env`)
   - MCP: `http://127.0.0.1:8000/mcp`
   - n8n: `http://localhost:5678`

این workflow از URL محلی MCP استفاده می‌کند. اگر n8n و MCP Server در دو محیط شبکه‌ای جدا اجرا شوند، آدرس MCP باید با آدرس قابل دسترس از محیط n8n جایگزین شود.

## Import و اجرا

1. در n8n وارد بخش Workflows شوید.
2. گزینه Import from File را انتخاب کنید.
3. فایل `workflows/nexusops-mcp-runtime-test-suite.json` را از مخزن محلی Import کنید.
4. workflow را باز کنید و از Manual Trigger گزینه Execute Workflow را اجرا کنید.
5. خروجی آخرین نود، یعنی `Evaluate Runtime Results` را باز کنید.
6. مقدار `summary.overall` و وضعیت هر مورد در `results` را بررسی کنید.

این workflow به‌صورت پیش‌فرض غیرفعال است و فقط با اجرای دستی آغاز می‌شود. هیچ داده‌ای در Elasticsearch ایجاد، حذف یا به‌روزرسانی نمی‌کند.

## آزمون‌های موجود

| شناسه | آزمون | معیار موفقیت |
|---|---|---|
| T01 | MCP tools/list | پنج ابزار اصلی NexusOps در فهرست ابزارها موجود باشند |
| T02 | بازیابی درس C002 | دقیقاً یک رکورد با course_id برابر C002 برگردد |
| T03 | شمارش فارغ‌التحصیلان | پاسخ موفق count با عدد صحیح نامنفی دریافت شود |
| T04 | Aggregate مهارت‌ها | گروه‌بندی بر اساس skill و دو metric عددی با aliasهای درخواستی دریافت شوند |
| T05 | فیلتر تو‌در‌توی AND/OR | شمارش با فیلتر ترکیبی بدون خطای اجرا انجام شود |
| T06 | دیتاست نامعتبر | خطای ساختاریافته با status برابر error دریافت شود؛ خطا نباید به نتیجه صفر تبدیل شود |

## تفسیر گزارش

- `PASS`: معیار همان آزمون در پاسخ واقعی MCP برقرار شده است.
- `FAIL`: پاسخ واقعی با قرارداد مورد انتظار تطبیق نداشته؛ فیلد `detail` علت اولیه را نشان می‌دهد.
- `summary.overall = PASS`: تمام شش سناریو در همان اجرای workflow موفق بوده‌اند.
- موفقیت این مجموعه به‌تنهایی صحت پاسخ‌نویسی مدل زبانی، رفتار multi-plan در workflow اصلی یا بازیابی پس از قطع ارتباط را اثبات نمی‌کند؛ این موارد در آزمون End-to-End workflow اصلی بررسی می‌شوند.

## عیب‌یابی

- خطا در `MCP Initialize`: وضعیت اجرای MCP Server، پورت 8000 و مسیر `/mcp` را بررسی کنید.
- خطا در `MCP Initialized Notify`: پاسخ HTTP و session/protocol headerهای MCP را بررسی کنید.
- خطای اتصال Elasticsearch: URL، نام کاربری و `ELASTICSEARCH_PASSWORD` در `.env` را بررسی کنید.
- شکست T02: وجود داده C002 در `university_courses` و مقدار واقعی `course_id` را بررسی کنید.
- شکست T04 یا T05: جزئیات خطا و فیلدهای واقعی indexهای `skill_mapping` و `university_graduates` را بررسی کنید.

گزارش اجرای workflow را همراه با خروجی JSON نود `Evaluate Runtime Results` نگه دارید تا بتوان آن را با اجرای بعدی مقایسه کرد.


## قرارداد Decode و تطبیق پاسخ

ارزیاب پاسخ هر فراخوانی را بر اساس JSON-RPC ID متناظر می‌کند؛ بنابراین ترتیب خروجی HTTP Request به‌تنهایی مبنای اتصال آزمون و پاسخ نیست. همچنین پیش از اجرای assertionها، wrapperهای MCP شامل `structuredContent` و مقدار JSON رشته‌ای در فیلد `result` به‌صورت بازگشتی Decode می‌شوند. این موضوع مانع از گزارش شکست کاذب در حالتی می‌شود که محتوای تحلیلی سالم، در یک wrapper رشته‌ای قرار گرفته باشد.

اگر پاسخ دارای ID تکراری باشد، آزمون به‌جای انتخاب دلخواه یک پاسخ، صریحاً شکست می‌خورد. اگر پاسخ transport فاقد JSON-RPC ID باشد، ارزیاب فقط در صورت وجود paired-item metadata از آن برای اتصال خطا به آزمون متناظر استفاده می‌کند.


## دروازه یکپارچگی پاسخ در Workflow اصلی

در نسخه سخت‌سازی‌شده Workflow اصلی، هر اجرای n8n با شناسه اجرای خود از مرحله ساخت درخواست MCP تا Context تحلیل و پاسخ نهایی ردیابی می‌شود. این شناسه برای مشاهده‌پذیری است و جایگزین JSON-RPC ID یا MCP Session ID نیست.

پیش از ساخت پاسخ نهایی، مجموعه Planها از نظر تعداد مورد انتظار، یکتایی شناسه‌ها، پیوستگی indexها، وضعیت correlation و وضعیت واقعی اجرا ارزیابی می‌شود. پاسخ‌های ناشناخته، شکست‌های اجرایی و وضعیت‌های نامعلوم موفقیت تلقی نمی‌شوند. این هشدار در حالت تحلیل متنی نیز حفظ می‌شود و دیگر با انتخاب response mode از خروجی حذف نخواهد شد.

وضعیت نهایی یکی از این مقادیر است:

- `success`: تمام Planها کامل، یکتا، هم‌بسته و با ساختار شناخته‌شده اجرا شده‌اند.
- `partial_failure`: مجموعه Plan کامل و هم‌بسته است، اما اجرای یک Plan شکست خورده یا ساختار یک پاسخ ناشناخته است.
- `incomplete`: تعداد/شناسه Planها یا هم‌بستگی پاسخ‌ها ناقص یا مبهم است.
- `unknown`: وضعیت اجرای حداقل یک Plan قابل تعیین نیست.

شناسه اجرای n8n فقط برای ردیابی همان execution است؛ برای سنجش جداسازی واقعی درخواست‌های هم‌زمان باید چند execution مستقل در n8n اجرا و شناسه‌ها و نتایج آن‌ها جداگانه بررسی شوند.
